# Relay · 鉴权准入实现方案

版本：待实现
前置：[plan.md](plan.md)（转接层，已完成）、[status.md](status.md)

---

## 一、要解决什么

现在任何能访问 `127.0.0.1:3080` 的本机进程，都能让 agent 干活，且 `source` 完全自报。这层要做三件事：

1. **外部应用先登记，用户批准，拿到凭证**——没批准的调不进来。
2. **每条消息按该应用的可信级别决定要不要再问一次用户。**
3. **用户能随时看、改、撤。** 撤销不需要应用配合。

`source` 从此不再只是标注，而是凭证绑定的主体。

---

## 二、模型

### 2.1 三个字段

| 字段 | 说明 |
|---|---|
| `source` | 应用标识，`[A-Za-z0-9_-]{1,64}`。登记后不可改名 |
| `fingerprint` | 凭证，32 字节随机 → base64url（43 字符）。只在发放时返回一次 |
| `level` | 0–3，见下 |

### 2.2 级别

| 级别 | 名称 | 行为 |
|:---:|---|---|
| 0 | 禁止 | 静默拒绝，**不弹窗**。用于被用户拒绝过的应用，避免骚扰 |
| 1 | 每条确认 | 每条消息都弹窗 |
| 2 | 信任用户主动发起 | `trigger:"user"` 直接放行；`trigger:"app"` 弹窗 |
| 3 | 完全信任 | 不弹窗 |

`trigger` 是调用方自报的：`user` 表示"用户点了按钮/说了话"，`app` 表示"应用自己发的"。级别 2 相信这个自报，级别 3 连问都不问。

**它与"是否放行"是两件事。** 应用发起的消息被用户点了一次"允许"，只是这次调用被允许，不代表这句话是用户说的。Relay 用一个独立的 `approved` 记录放行结果，绝不把它折成"用户发言"。

**首次接入一律给级别 1。** 级别不在接入弹窗里选，用户之后在设置页自己改——弹窗只问"允不允许"，两个按钮。

### 2.3 拒绝是终局

用户选"拒绝"时写入 `level:0` 且**不发放凭证**。之后该 source 再申请直接返回拒绝，不弹窗。要恢复只能由用户在管理界面里解除。

这条是刻意的：被拒绝的应用如果能反复弹窗，用户会被骚扰到盲点同意。

## 三、存储

用一个凭证记录，一条 source 一条：

```
key:     relay/<source>
kind:    grant
payload: { fingerprint: string | null, level: 0|1|2|3 }
```

用 `ctx.credentials`：

- `modifyRecord(key, mutate)` 是唯一写路径，且是**独占读改写**——轮换指纹时不会丢写。
- `listRecords()` 返回全部 `{key, kind}`，按前缀 `relay/` 过滤即得登记表。
- 记录是持久的，重启不丢；`deleteRecord` 就是"删除登记"。

`fingerprint` 为 `null` 表示只有禁止记录、没有凭证。

**校验用常量时间比较**（`crypto.timingSafeEqual`，长度不等时先返回 false）。

## 四、流程

### 4.1 首次接入

```
POST /x/relay/fingerprint   {"source":"my-app"}
```

1. 校验 `source` 格式。
2. 读记录：
   - 已有凭证 → `409 ERR_SOURCE_EXISTS`（不回旧凭证）
   - 只有 level 0 记录 → `403 ERR_ACCESS_DENIED`，**不弹窗**
3. 弹原生确认框，阻塞等待（60 秒）。
4. 用户选择：
   - **拒绝** → 写 `{level:0, fingerprint:null}` → `403 ERR_ACCESS_DENIED`
   - **允许** → 写 `{level:1, fingerprint:随机}` → `200 {source, fingerprint}`
5. 没有桌面 → `503 ERR_AUTH_UNAVAILABLE`，**不落任何记录**
6. 超时或关掉窗口 → `504 ERR_AUTH_TIMEOUT`，不落记录

级别固定给 1。用户要更高信任，自己去设置页改——这样接入弹窗只需要两个按钮。

### 4.2 消息准入

`POST /x/relay/submit` 新增两个字段：

| 字段 | 必填 | 说明 |
|---|:---:|---|
| `fingerprint` | ✅ | 凭证 |
| `trigger` | | `user` / `app`，缺省 `app`。表示谁发起的 |

顺序：

1. 原有字段校验（`content` / `source` / `session` / `timeout`）。
2. **验凭证**。失败 → `401 ERR_INPUT_FINGERPRINT`。此时不检查 session、不生成编号。
3. 读级别：
   - 0 → `403 ERR_ACCESS_DENIED`，不弹窗
   - 1 → 需要确认
   - 2 → `trigger=user` 跳过确认，`trigger=app` 需要
   - 3 → 不确认
4. 需要确认时弹窗等待：
   - 允许一次 → 本次 `approved=true`；`trigger` 不变
   - 拒绝 → `403 ERR_AUTH_DENIED`
   - 超时 → `504 ERR_AUTH_TIMEOUT`
   - 无桌面 → `503 ERR_AUTH_UNAVAILABLE`
5. 构造 content 包装时写入最终确认状态。
6. 其余同 v1（投递、关联、排队作废）。

**不做 session 忙预检。** v1 的语义是排队而不是拒绝，加了忙检查会变成两套准入：确认前拒一次、进队后又排一次。而且从检查到入队之间的状态本来就会变，预检挡不住什么。排队上限（10 分钟作废）已经约束了"迟到的意图"。

### 4.3 消息包装

```json
{"type":"external_request","source":"my-app","trigger":"app","approved":true,"content":"调用方原文"}
```

必须序列化——外部原文作为 JSON 字符串字段，闭合不了引号，伪造不出包装结构。这是注入边界。

`source` 字段不承担归属职责（DSH 的 `MessageSource` 不进模型视野），归属只走这里。

### 4.4 管理（设置页）

管理操作分两类，**分界线是"放松还是收紧"**：

- **收紧**（降级、撤销、删除）：立即生效，不确认。撤销权限不需要本人再点一次。
- **放松**（升到更高级别、重置凭证、解除禁止）：**必须过一次原生确认框**。

这样处理的原因：设置页和调用方一样走本地 HTTP，本机进程可以伪造请求。但放松授权要过原生弹窗，弹窗只能由真人点——请求伪造成了，确认伪造不了。于是不需要一个"安全通道"，只需要一个"人类证明"。

| 操作 | 类型 | 行为 |
|---|---|---|
| 列表 | 读 | 返回 source / level / 是否有凭证 |
| 降级、撤销 | 收紧 | 改成 0–2，立即生效；改成 0 时取消该 source 待处理的确认 |
| 升级 | 放松 | 改成比现在高的级别，先弹确认 |
| 解除禁止 | 放松 | 只对"无凭证的 level 0"可用，删记录让应用重新申请，先弹确认 |
| 重置凭证 | 放松 | 生成新的，级别保留，旧凭证立即失效，先弹确认 |
| 删除 | 收紧 | 凭证和级别一起删，回到未登记状态 |

- `GET /x/relay/sessions` 也要验凭证——会话名本身就是信息。
- `GET /x/relay/sources` 是设置页读列表用的，不要求凭证。它只暴露"有哪些应用接过入"，不暴露内容。本机进程看得到这份名单，但改不动（见上）。
- 级别上升、重置凭证、解除禁止会弹窗；降级、撤销、删除不弹窗。
- 管理接口的路径单独一组，和任务的 `/submit`、`/result` 分开。

## 五、弹窗

### 5.1 位置：操作系统原生

两个需要问用户的场景都走原生弹窗：首次接入，以及级别 1 / 2 的消息确认。

这样做的关键收益不是好看，是**应答通道问题不存在**。弹窗由操作系统渲染在主机屏幕上，只有真人能点；不需要 Client↔Host 通道，也不需要把应答塞进那个未鉴权的 HTTP 面——后者会让任何本机进程伪造"我同意"，整套鉴权变成摆设。

DSH 已有同类先例：目录选择器的 native 后端（macOS 脚本驱动 AppKit 面板、Windows 拉起子进程、Linux Zenity/KDialog）。

### 5.2 形态

只有两个按钮：**允许 / 拒绝**。

Windows / WSL 上是**右下角的置顶小窗口**（toast 形态），不占屏幕中心、不打断当前操作；macOS 和 Linux 仍是居中的系统对话框——那两边用脚本画角窗要额外依赖图形工具链，暂时不做。

消息确认框会带**请求内容预览**：正文放在可滚动的只读框里，窗口默认只露出几行，点「展开全文」长到接近整屏再点「收起」。用户得先看见应用要说什么，才谈得上允许不允许——只显示来源名不算知情。

| 场景 | 文案 | 允许后 |
|---|---|---|
| 首次接入 | 应用 `{source}` 请求接入 Relay，是否允许？ | 发放凭证，级别 1 |
| 消息确认 | 应用 `{source}` 请求发送一条消息，是否允许？ | 本次放行 |

级别不在弹窗里选。

### 5.3 命令

退出码即答案，`0` = 允许，不需要解析输出：

```
macOS    osascript -e 'display dialog "…" buttons {"拒绝","允许"} default button "允许"'
Windows  powershell -NoProfile -NonInteractive -Command "Add-Type -AssemblyName System.Windows.Forms; [System.Windows.Forms.MessageBox]::Show('…','Relay',[System.Windows.Forms.MessageBoxButtons]::YesNo)"
Linux    zenity --question --text=… --ok-label=允许 --cancel-label=拒绝   （KDialog 兜底）
```

### 5.4 实现要点

- 走 `ctx.subprocess.spawn`，不要自己拼 shell；平台工具缺失要报可读的错，不要静默降级。
- **60 秒超时必须 kill 子进程**，否则窗口一直挂在桌面上没人管。调用方 abort 时同样要 kill。
- 用户直接关掉窗口按"拒绝"处理，不按超时。
- **同一时刻只允许一个弹窗**，其余 FIFO——否则用户会同时收到多个窗口叠在一起。
- 文案固定，`source` 只嵌在固定句式里。应用名是自报的，固定句式能防止它伪装成系统提示。
- 等待一结束（允许/拒绝/超时/取消）立刻清掉队列项并 kill 进程。

### 5.5 没有桌面时

- 判定：macOS 看是否有登录会话，Windows 常驻，Linux 看 `DISPLAY` / `WAYLAND_DISPLAY`。
- 没有桌面时，需要弹窗的操作直接失败 `ERR_AUTH_UNAVAILABLE`，不落任何记录。
- **level 0 和 level 3 不受影响**——它们不弹窗，无桌面也能用。
- 从另一台机器用浏览器访问 GUI，也属于"主机没有可交互桌面"，需要人到主机上操作一次。

**不做网页兜底。** 一旦允许网页兜底，就得重新解决"怎么证明点按钮的是真人"——那正是原生弹窗替我们绕掉的东西。

### 5.6 设置页

**位置：顶层设置面板的左侧导航里新增一页**，和「通用」「模型」「插件」「外观」并列，名字叫「应用权限」。不放在插件页的标签下——插件页回答"装了什么、开没开"，用户查权限不会去那里翻。

页面是一张表，一行一个应用：

```
应用        级别        凭证      操作
qq-bridge   完全信任    已持有    改级别 · 重置凭证 · 删除
wallpaper   每条确认    已持有    改级别 · 重置凭证 · 删除
old-app     禁止        —         解除禁止
```

表头上方一段说明，讲清楚被允许的应用实际能做什么——"完全信任"四个字不够，用户得知道那意味着能让 agent 做任何事。

弹窗文案里带一句"之后可在设置 → 应用权限中调整"，让用户事后找得到。系统弹窗放不了链接，但这句提示够用。

**为什么不是浮层**：授权是长期状态，需要一次看全、反复回来改。确认用弹窗，管理用页面，两者不混。

写入走管理接口（见 §4.4）。放松授权的操作必须过一次原生确认框——本机进程能伪造请求，但伪造不了真人点击。

## 六、错误码

| code | HTTP | 场景 |
|---|---|---|
| `ERR_TRIGGER` | 400 | `trigger` 不是 `user` / `app` |
| `ERR_INPUT_FINGERPRINT` | 401 | 缺凭证或不匹配（不暴露 source 是否存在） |
| `ERR_ACCESS_DENIED` | 403 | level 0，静默拒绝 |
| `ERR_AUTH_DENIED` | 403 | 用户当场拒绝这条 |
| `ERR_AUTH_TIMEOUT` | 504 | 等待超时 |
| `ERR_AUTH_UNAVAILABLE` | 503 | 没有在线界面 |
| `ERR_SOURCE_EXISTS` | 409 | 重复申请 |
| `ERR_SESSION_BUSY` | 409 | 会话忙（与现有 `ERR_SESSION_BUSY` 同码） |

沿用的：`ERR_REQUEST_JSON` / `ERR_CONTENT` / `ERR_SOURCE` / `ERR_SESSION` / `ERR_TIMEOUT` / `ERR_RESULT_NOT_FOUND` / `ERR_SESSION_OUTSIDE_WORKSPACE` / `ERR_QUEUE_EXPIRED`。

## 八、验收

```
□ 未登记 source 提交 → 401
□ 申请凭证 → 系统原生弹窗出现，与浏览器是否打开无关
□ 选"拒绝" → 403，且再次申请不再弹窗
□ 选"允许" → 拿到凭证，级别为 1
□ level 1 → 每条消息弹窗；拒绝的那条不投递
□ 在设置页改成 level 2 → trigger:user 放行，trigger:app 弹窗
□ 在设置页改成 level 3 → 不弹窗
□ 弹窗 60 秒无响应 → 504，且没有写入任何记录，子进程被杀掉
□ 没有桌面（或从另一台机器访问）→ 503，没有写入；level 3 的调用仍然可用
□ 同一时刻两个申请 → 弹窗排队，不是叠在一起
□ 会话忙时提交 → 409，且不弹窗
□ 轮换凭证 → 旧凭证立刻 401，级别保留
□ 改成 level 0 → 待决请求被取消，后续静默拒绝
□ 本机进程直接 POST「升到 level 3」→ 弹出原生确认框，无人点击则不生效
□ 本机进程直接 POST「降到 level 0」→ 立即生效（收紧不需要确认）
□ 外部原文里的引号/花括号伪造不出包装结构
```

## 九、不在本方案内

- 应用身份的**密码学证明**（当前 `source` 仍是自报字符串，凭证只证明"知道这个 source 的密钥"）。真要证明"是哪个程序"，需要代码签名或操作系统凭据，超出范围。
- 操作审计（谁在什么时候改了什么级别）。
- 限流。
- 跨机器调用。
