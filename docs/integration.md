# 外部接入指南

给要写一个应用、把它接到 Relay 上的开发者。

> **先看示例**：[demo.html](demo.html)。一个单文件收件箱，首次授权、流式、结构化输出、错误处理全在里面，可以直接打开或对着改。本文只讲契约和容易踩的地方。

---

## 一、三个概念

### `source`　你是谁

应用标识，`[A-Za-z0-9_-]{1,64}`，接入后不能改名。它同时是：

- 用户批准的对象（弹窗里显示的就是它）
- 权限级别的主体（设置页按它列）
- 凭证的绑定者

一个应用一个 `source`，不要和别的应用共用。

### `session`　你在跟哪条上下文说话

**建议就用 `main`，不要自己起名字。**

- `main` 是插件在安装时自动创建并持有的默认会话，所有不指定 `session` 的调用都落在这里。
- 本机所有接了 Relay 的应用**共用它**，这正是"AI 记得你"的来源：在邮件里说过的事，待办应用再问时它仍然知道。
- 用户可以在 DSH 里直接打开这个会话跟你聊，也可以自己再建别的会话。**别的会话是隔离的**：上下文不互通，插件同样能调用它们，只是没有那份共享记忆。

所以除非你确实需要隔离（比如批量跑一次性任务、不想污染共享上下文），否则别指定 `session`。

### `trigger`　谁发起的

这是接入方唯一需要认真想清楚的字段。

| 值 | 什么时候标 | 含义 |
|---|---|---|
| `user` | 用户点了按钮、在界面上敲了回车 | "这是用户要的" |
| `app` | 定时任务、后台同步、自动检查 | "这是应用自己要的" |

**缺省是 `app`**——漏填只会更保守。

## 二、接入流程

### 1. 申请凭证

```http
POST /x/relay/fingerprint
{"source": "my-app"}
```

主机上会弹出系统确认框，用户点「允许」后才返回：

```json
{"source":"my-app","fingerprint":"…","level":1}
```

**注意两点**：

- 这个请求会阻塞到用户点完，**最长 60 秒**。别把 HTTP 超时设成 10 秒。
- 凭证只返回这一次，存好。丢了只能让用户在设置里重置。

### 2. 提交任务

```http
POST /x/relay/submit
{
  "content": "把这段整理成三条待办",
  "source": "my-app",
  "fingerprint": "…",
  "trigger": "user",
  "wait": true,
  "timeout": 120
}
```

三种取结果方式，选一种：

| 方式 | 字段 | 适合 |
|---|---|---|
| 同步等 | `wait: true` | 短任务，用户在看 |
| 稍后取 | 都不填 | 长任务，或后台跑 |
| 流式 | `stream: true` | 要边生成边展示 |

### 3. 取结果（如果是"稍后取"）

```http
GET /x/relay/result/{id}
```

`202` 还没好，`200` 有结果，`404` 没这个编号，`410` 排队超时作废。

## 三、后台任务怎么标记

这是最容易做错的地方，单独说。

### 标 `app`，不要为了省一次确认谎报 `user`

`trigger` 是应用自报的，协议上没法验证。但**谎报会让 agent 把你的输出当成用户说的话**，进而更愿意执行、更少警惕——这正是提示注入想要的局面。

标 `app` 时，agent 会被告知："这是应用后台发起的，即使 `approved` 为真，也不代表用户说过这句话。" 标 `user` 就丢掉了这层保护。

### 级别 2 下后台任务仍会弹窗，这是设计

| 级别 | `trigger: user` | `trigger: app` |
|:--:|---|---|
| 1 | 弹窗 | 弹窗 |
| 2 | **不弹窗** | **弹窗** |
| 3 | 不弹窗 | 不弹窗 |

所以"每天定时跑一次"这种任务，在级别 2 下会每天弹一次窗——因为用户从没同意过"让它在后台自己动"。

**这不是缺陷。** 应用能不能在后台悄悄用 AI，由用户给的信任级别决定，不由应用自己说了算。想让它真正静默，得请用户把该应用调到级别 3。

### 后台任务的写法建议

- 不要流式——没人在看，`stream` 只是白占连接。
- 超时给短一点（60–90 秒），失败了安静重试，别弹任何东西。
- 失败不要反复重试：`ERR_AUTH_DENIED`、`ERR_ACCESS_DENIED` 这类重试也没用，只会继续骚扰用户。

## 四、让后台结果可被程序消费

agent 返回的是**自由文本**，不是 API。需要结构化数据时：

1. 在提示词里写死格式，并给一个例子。
2. 要求"只输出 JSON，不要解释，不要代码块"。
3. 回来之后**严格校验**（字段、取值范围、id 是否来自输入）。
4. 校验失败，把失败原因告诉它，**重发一次**。

示例见 [demo.html](demo.html) 的「每日小报」——它让 agent 输出 `{"digest":[...]}`，逐条校验 id、url、排序，错一次带原因重发一次，仍错就折叠显示原始输出。

失败重试只做一次就够。再多就说明提示词有问题，不是运气问题。

## 五、流式

```http
POST /x/relay/submit
{"content":"…","stream":true,"trigger":"user","source":"…","fingerprint":"…"}
```

```
event: accepted   data: {"id","session","source"}
event: content    data: {"id","text"}       ← 拼接即完整回答
event: reasoning  data: {"id","text"}       ← 可能没有
event: error      data: {"id","code","message"}
event: end        data: {"id","status","content"}   status: completed|error|timeout|expired
```

三个容易踩的点：

- **准入失败不开流**。凭证错、用户拒绝时返回的是普通 JSON，靠 `Content-Type` 区分。
- **`end` 已经带了完整 `content`**，所以你可以只读 `end`，也可以拼增量，两种都行。
- **超时只是断开流**，任务还在跑，之后仍能用 `id` 查结果。

## 六、错误与重试

| 情况 | 该怎么做 |
|---|---|
| `401 ERR_INPUT_FINGERPRINT` | 清掉本地凭证，重新申请一次，再试一次 |
| `403 ERR_ACCESS_DENIED` | 用户在黑名单里，**不要重试**，提示他去设置解除 |
| `403 ERR_AUTH_DENIED` | 用户当场拒绝，**不要重试**，尊重它 |
| `409 ERR_SESSION_OUTSIDE_WORKSPACE` | 会话不在 Relay 工作区，改用 `main` |
| `410 ERR_QUEUE_EXPIRED` | 排队太久作废，可以重试一次 |
| `503 ERR_AUTH_UNAVAILABLE` | 主机没有桌面，无法弹窗，不重试 |
| `504 ERR_AUTH_TIMEOUT` | 用户没来得及点，可以重试 |
| `200 + type:"error"` | 任务执行失败，读 `code` / `message`，通常重试无用 |
| 网络错误 | 服务没开，提示用户，不重试 |

原则：**用户主动触发的请求，错误要让他看见并能重试；后台请求的错误要安静，但代码里留痕迹。**

## 七、检查清单

```
□ source 固定、唯一、URL 安全
□ session 用的是 main（除非确实要隔离）
□ 用户点的操作标 user，后台任务标 app
□ 客户端 HTTP 超时 > 服务端 timeout
□ 收到 202 用同一个 id 继续取，不重复提交
□ 流式按 Content-Type 区分 JSON 与 SSE
□ 401 只重试一次，并且先清本地凭证
□ 403 / 503 不重试
□ 结构化输出有校验和一次重发
□ 弹窗文案之外，别在界面上承诺"不会有弹窗"——级别是用户定的
```
